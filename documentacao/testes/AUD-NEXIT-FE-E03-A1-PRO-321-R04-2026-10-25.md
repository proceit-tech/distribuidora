## Achado novo E03-A1-F002-R04 — ALTA — SQL ainda aceita cenários que o gateway considera indeterminados

**Contrato do gateway:** `gateway.ts::interpretarRecepcion`, aproximadamente linhas 505–518 e 535–541, consulta `Number(raiz.rechazados)` (contador no topo) e `buscar(raiz, CLAVES_CDC)`/lote/eco que **retorna a primeira correspondência** (linhas 396–415). O SQL `fe_e03_recepcion_confirmada`, linhas aprox. 243–307, percorre todas as ocorrências com `fe_e03_valores_por_clave` e **ignora candidatos com tipo/forma inválidos**, podendo aceitar outro candidato posterior que o gateway não utilizaria. A alegação de que o SQL nunca aceita mais do que o gateway **ainda não está demonstrada**.

**Contraexemplo concreto A — contador de rejeições como texto/booleano:**
```json
{"status":"success","nro_lote":"LOTE123","rechazados":"1"}
```
No gateway, `Number("1") > 0` é verdadeiro, `rechazados` vinculados ao próprio documento ausentes, e `interpretarRecepcion` devolve `ENVIO_INDETERMINADO` (não `OK`). No SQL, `fe_e03_valores_por_clave(..., ['rechazados'])` encontra `"1"` JSON string; o `IF` só bloqueia array não vazio ou valor JSON do tipo number > 0, **ignora a string**, e o lote válido permite `true` → **CIERRE OK/ENVIADO indevido**. `rechazados:true` também gera `Number(true)=1` no gateway mas é ignorado no SQL. São representações aceitas pela lógica TS atual, mesmo que atípicas no provedor.

**Contraexemplo concreto B — primeiro CDC ilegível, posterior CDC válido:**
```json
{"status":"success","cdc":"INVALIDO","response":{"cdc":"<CDC válido de 44 dígitos correspondente ao próprio documento>"}}
```
Sem lote nem eco. `gateway.ts::buscar` retorna o `cdc` do topo, a função `cdcInformado` fica `null` por não haver 44 dígitos, e a função TS conclui `ENVIO_INDETERMINADO`. No SQL, a função recursiva ignora o `cdc` inválido e encontra o CDC válido aninhado, atribuindo `v_cdc=true`, e **pode confirmar OK**. Analogamente, candidatos `lote`/eco de tipo inválido na primeira posição e válidos aninhados podem criar outro falso positivo se o SQL os ignorar. Os valores são ilustrativos, não documentos reais.

**Correção necessária:** sem duplicar arbitrariamente o parser TypeScript, alinhar o SQL de forma **estritamente conservadora**:
- contador de `rechazados` do nível principal: tratar tipos equivalentes que `Number(...)` considera positivos (numéricos como texto, boolean true) e rejeitar a recepção; para formato ambíguo, rejeitar, não presumir sucesso;
- quando houver múltiplos candidatos de lote/CDC/eco, **não ignorar candidatos não nulos, não vazios e malformados**, pois o gateway pode ter escolhido um deles antes do candidato válido. Rejeitar a confirmação em caso de tipo/estrutura incoerente, mesmo que outro candidato pareça válido;
- preservar F002-R03 (rejeição de terceiros via `OtrosDocumentosOmitidos`/aceptados), F001/F003/F004; não ampliar para alterações TS, estados SIFEN, NEX-054, UI ou outra migration.
- conferir as **todas condições prévias de `interpretarRecepcion`** de uma só vez para evitar novos falsos positivos; se o espelho SQL não tiver dados suficientes, bloquear `OK` conservadoramente, documentando limitação (falso negativo é aceitável; falso positivo NÃO).
