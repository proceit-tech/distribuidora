## 2. Dirección — dos datos que NO deben confundirse

**A. Domicilio fiscal del RECEPTOR:** `lib/facturacion/emision.ts::receptorDe` lee `clientes` + `direcciones_cliente` con `es_fiscal OR tipo='FISCAL'`, en el orden indicado. `lib/facturacion/payload-fe.ts::construirPayloadFE` coloca `dDirRec = receptor.direccion` y `dNumCasRec = receptor.numeroCasa` (si no hay dirección fiscal, `dDirRec` se emite `null`; `dNumCasRec` nulo). **Seleccionar un destino de mercadería NO cambia el domicilio fiscal; prohibido copiarlo a `dDirRec` por defecto.** Si la dirección fiscal sale vacía, verificar que exista la dirección fiscal en `Clientes`, que esté realmente marcada y que NEXIT la resuelva con empresa y cliente correctos.

**B. Dirección de ENTREGA seleccionada:** `app/(private)/facturas/nueva/page.tsx::cuerpoFactura` manda `direccionEntregaId` del destino elegible. `lib/facturacion/emision.ts` la valida para la empresa/cliente con `resolverEntrega(opcionesEntrega(...))`. `lib/facturacion/info-adicional.ts::lineaEntrega` compone `Dirección de entrega: NOMBRE — CALLE, NÚMERO, CIUDAD...` como texto comercial. `emision.ts::prepararFactura` lo añade a `infoAdicional` mediante `componerInfoAdicional` y `payload-fe.ts` lo integra en el **JSON de emisión** como **`dInfAdic` (J003)**. Este es **campo comercial del JSON del proveedor, NO sustituto del domicilio fiscal ni necesariamente del XML firmado**. El texto final y su huella se muestran en la previa y se guardan como snapshot de solicitud inmutable; un reintento de la misma emisión reutiliza el snapshot persistido.

**Conclusión SOLO estática:** el código actual **sí tiene ruta para enviar la dirección de entrega dentro de `dInfAdic`**, si se eligió, fue validada y se construyó una nueva emisión. No hay base para afirmar que una factura concreta efectivamente incluyó el texto, ni que se haya transmitido al gateway o que el proveedor lo haya impreso, sin inspeccionar evidencia de esa operación.

## 3. Por qué el KuDE puede aparecer vacío

`app/api/documentos/[id]/kude/route.ts` obtiene el PDF usando `lib/facturacion/shared.ts::obtenerKude` → `gateway.ts::obtenerKudeGateway` → `POST /api/kude`. El NEXIT **presenta el PDF entregado por el proveedor**, no genera ni maqueta el PDF KuDE localmente. El contrato del KuDE usa identidad fiscal `dEst`, `dPunExp`, `dNumDoc`, `dSerieNum`, `tipoDoc`; **no manda un destino de entrega en el POST de descarga**. El PDF se genera del documento conocido por el proveedor. El asunto de **impresión de `dInfAdic` en el KuDE** ya corresponde a [PRO-298](https://linear.app/proceit/issue/PRO-298/cm-v1-provedor-validar-cabecera-y-formato-kude-fencr-con-proveedor-api), validación humana con proveedor, **no a cambiar arbitrariamente el JSON SIFEN ni editar PDFs fiscales retornados**.
