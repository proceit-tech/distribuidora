## Convenções deste arquivo

- **Persistência** descreve o destino real do campo: `API-SQL` = o código SQL grava ou lê a coluna; `DEMO-localStorage` = só existe no mock/`localStorage`; `DERIVADO` = calculado ou obtido por JOIN; `SESSAO` = vem da sessão, não do usuário; `UI-only` = só estado de tela (subseção própria). **Importante:** todo campo `API-SQL` que o formulário também envia hoje é gravado pela UI apenas em `localStorage` (ver DIV-01); a coluna Persistência mostra o destino SQL previsto pelo código da API.
- **Tela(s):** `Lista`, `Nuevo`, `Editar`; `—` = o campo não aparece em tela; `— (só tipo/mock)` = existe no tipo TS/mock/API, mas o formulário não tem input.
- **Escopo:** o módulo é `EMPRESA` (coluna `company_id`); nenhum campo usa `branch_id` ou `warehouse_id` (o código não tem regra por filial/depósito para fornecedores — ver perguntas abertas). Catálogos globais aparecem como `GLOBAL (catálogo)`.
- **Etiqueta `[SENSÍVEL: PROVEEDORES_BANCARIO.VER/EDITAR]`:** dado financeiro controlado pelo REQ-2026-002 (permissões `DATO_SENSIBLE`; sem a permissão o dado deve vir mascarado — `MATRIZ-PERMISOS-REQ-2026-002.md:34,101,168`). **No código atual (`0dbb013`) não existe nenhuma checagem dessas permissões**: a API só exige sessão e a UI não verifica permissão (ver DIV-23).
- Os nomes ES são o que o SQL do código usa; os nomes EN da coluna Alvo são só proposta. Os valores de enum (`JURIDICA`, `HOMOLOGADO`...) ficam como no código; traduzi-los é decisão pendente.
- O tipo `ProveedorBody`/`*Input` (corpo do POST) vive em `app/api/proveedores/route.ts:64-177`; os tipos de tela em `types/proveedores.ts`.

## Regras confirmadas no código

1. Todo fornecedor pertence à empresa da sessão: o INSERT usa `session.user.empresaId` e o SELECT filtra `p.empresa_id = $1` (`route.ts:391,444,671`). Sem sessão a API responde 401 (`route.ts:375-382,542-549`).
2. A criação é transacional: `BEGIN`, INSERT do cabeçalho e dos filhos, `COMMIT`; qualquer erro faz `ROLLBACK` (`route.ts:632-633,869,875`).
3. Obrigatórios do cabeçalho na API: tipo de documento, número do documento, razão social e país válido de 3 letras maiúsculas (`route.ts:565-568`). País vazio assume `PRY` (`route.ts:560`).
4. País `PRY` exige tipo de documento `RUC` (API `route.ts:570-572`; UI `proveedor-form.tsx:311-318`, que também força `RUC` ao escolher PRY em `:612-614`).
5. RUC: número com 3 a 8 dígitos e DV com exatamente 1 dígito (`route.ts:573-576`; UI `proveedor-form.tsx:320-330`). O DV só é gravado se o tipo for RUC (`route.ts:676`). O código **não** calcula nem confere o DV.
6. Comprimentos máximos da API: tipo de documento 30; número 50 (sem espaços); DV 1; razão social 200; nome fantasia 200; país 3; e-mail 150; e-mail de pagamentos 150; site 300; telefone 50; observação 2000; condição de entrega 500 (`route.ts:556-563,678,681,695,702`).
7. E-mail com regex simples e site com URL http/https (`route.ts:259-272,578-580`).
8. Faixas: dia de pagamento 1-31; prazo de entrega ≥ 0; dias de confirmação ≥ 0; desconto 0-100; monto mínimo ≥ 0; calificación 0-100 (`route.ts:589-596`). Defaults: desconto 0, monto mínimo 0 (`route.ts:585-586`).
9. Listas de valores: estado de homologação (6), nível de risco (5), método de transporte (6); defaults `PENDIENTE` e `NO_EVALUADO` (`route.ts:189-205,598-603`).
10. Datas no formato `YYYY-MM-DD`; fim da relação ≥ início; vencimento da homologação ≥ homologação (`route.ts:220-227,605-610`).
11. Referências validadas: grupo e meio de pagamento na mesma empresa e ativos; condição de pagamento, moeda, incoterm e país ativos no catálogo global (`route.ts:274-311,641-648`).
12. Booleanos: `permiteEntregaParcial` default true; `permiteAnticipos` e `requiereOrdenCompra` default false; `activo` sempre `true` na criação (`route.ts:667,689-690,705`).

## Regras que dependem de definição

1. **Permissões** `PROVEEDORES.VER/CREAR/EDITAR/ELIMINAR/EXPORTAR` e `PROVEEDORES_BANCARIO.VER/EDITAR`: definidas no REQ-2026-002 (mascaramento sem permissão; `POST` com contas exige `EDITAR`), mas inexistentes no código (DIV-23). A matriz marca o recurso bancário como DATO_SENSIBLE, sem perfil padrão, só concessão individual com dupla aprovação.
2. Mascaramento/criptografia de `numero_cuenta`, `iban`, `codigo_swift` e `documento_titular`; se o documento `CERTIFICADO_BANCARIO` também cai sob `PROVEEDORES_BANCARIO`.
3. **Retenções:** aplicação (onde e como incide em compra/pagamento), alíquotas legais permitidas, obrigatoriedade do certificado, vínculo com `impuesto_id`/`taxes`, sobreposição de vigências, normativa SET/SIFEN.
4. Cálculo do DV do RUC (módulo 11) e formato de documentos não-RUC (CI, passaporte, CUIT).
5. Homologação: se `VENCIDO` é automático pela data; se `HOMOLOGADO` exige datas; efeito do estado/risco/`bloqueado` sobre compras e pagamentos; origem da calificación.
6. `bloqueado` / `motivo_bloqueo`: quem altera, motivo obrigatório, efeito.
7. Precisão de `monto_minimo_compra` (2 ou 4 casas) e moeda (a do fornecedor); precisão de percentuais.
8. `condiciones_pago`: global ou por empresa (REQ-2026-002 §3.4, pendente); `taxes` global com habilitação por empresa.
9. Sequência e unicidade de `code` por empresa; unicidade de documento por empresa (hoje por constraints NAO_VERIFICADO).
10. Armazenamento real dos arquivos de `supplier_documents` (hoje só nome e URL sem validação).
11. Alcance por filial/depósito para fornecedores (hoje só empresa).
12. Tradução dos valores de enum (JURIDICA, HOMOLOGADO...) para inglês.
13. API de edição, inativação e consulta de detalhe (inexistentes).
